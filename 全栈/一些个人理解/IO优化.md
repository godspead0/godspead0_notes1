从“同步阻塞（BIO）”转向“Reactor / Proactor 异步非阻塞”，是高并发服务端架构为解决单机海量并发连接（C10K/C1000K 问题）经历的两次关键技术演进。其本质转变在于**解耦连接与线程的绑定关系**，并优化**内核空间与用户空间的数据搬运时机**。



## 演进的三种核心模型

### 1. 同步阻塞（BIO：Blocking I/O）

BIO 采用“一个连接对应一个处理线程”的模式。



- **执行流程**：应用线程发起 `read()` 调用后，线程进入休眠阻塞状态。直到网卡接收完数据包并写入内核缓冲区，内核再将数据完整拷贝到用户态内存，系统调用才返回唤醒线程。
- **核心瓶颈**：操作系统单线程默认占用约 512KB~1MB 栈内存。当并发连接达到数万时，不仅内存迅速耗尽，CPU 绝大部分时间都浪费在成千上万个线程的上下文切换上。

### 2. Reactor 模式（同步非阻塞 + I/O 多路复用）

Reactor 是一种**基于事件驱动的“就绪通知”模型**，核心思想是“单线程管理多连接”。



- **执行流程**：
    1. 应用将多个 Socket 连接注册到事件分发器（Reactor）中，底层依赖 OS 的 I/O 多路复用调用（如 Linux 的 `epoll`）。
    2. Reactor 循环监听事件。当某个 Socket 有数据到达内核缓冲区时，内核发出**可读就绪事件**。
    3. Reactor 将就绪事件派发给对应的 Handler（处理器）。
    4. **Handler 亲自调用非阻塞 `read()`，在用户态下将数据从内核缓冲区拷贝到进程内存**，随后进行业务逻辑处理。
- **为何仍是同步**：虽然线程不再空等网络数据到达，但**数据从内核向用户空间搬运的过程依然由应用线程同步完成**，拷贝期间该线程仍然处于等待状态。
- **典型实现**：Netty、Nginx、Redis、Node.js。

### 3. Proactor 模式（异步非阻塞 AIO）

Proactor 是一种**基于内核托管的“完成通知”模型**，实现了彻底的异步。



- **执行流程**：
    1. 应用发起读操作时，不仅要指定 Socket，还要预先分配好一块用户态缓冲区（Buffer）的内存指针一并交给内核，随后请求立即返回，线程继续做其他工作。
    2. 内核负责监听数据到达，并在数据就绪后**主动将数据从内核空间拷贝至应用提供的 Buffer 中**。
    3. 当整个拷贝彻底完成后，内核生成**完成事件**，通知 Proactor 分发器唤醒或回调处理函数（Completion Handler）。
    4. 应用拿到 Buffer 时，数据已经是完整的就绪状态，直接执行业务计算。
- **为何是纯异步**：“等数据”和“搬数据”两个阶段全部由内核在后台完成，应用线程全程不产生任何 I/O 停滞。
- **典型实现**：Windows 的 IOCP、现代 Linux 的 `io_uring`。

## 架构特性全景对比

| **评估维度**       | **同步阻塞 (BIO)**       | **Reactor (I/O 多路复用)**             | **Proactor (异步 I/O)**              |
| ------------------ | ------------------------ | -------------------------------------- | ------------------------------------ |
| **通知类型**       | 无通知（调用即挂起等待） | **就绪通知**（数据到了，快来读）       | **完成通知**（数据已读完，快来处理） |
| **数据搬运主体**   | 应用线程同步拷贝         | **应用线程**同步拷贝                   | **操作系统内核**后台异步拷贝         |
| **线程与连接比**   | 1:1（强绑定）            | 1:N（一个线程轮询成千上万连接）        | 1:N（完全由事件回调驱动）            |
| **POSIX 规范定义** | 同步 I/O                 | 同步 I/O                               | 异步 I/O                             |
| **底层系统调用**   | `read` / `write`（阻塞） | `select` / `poll` / `epoll` / `kqueue` | Windows `IOCP` / Linux `io_uring`    |
