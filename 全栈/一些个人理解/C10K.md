**C10K 问题**（Concurrent 10,000）与 **C1000K 问题**（Concurrent 1,000,000，即 C1M）是指单台服务器在特定的硬件与操作系统约束下，如何同时支撑**一万**与**一百万**个并发网络连接的技术瓶颈与演进命题。



这两个概念分别代表了高并发架构发展史上的两个里程碑，标志着服务端的瓶颈从“线程与调度模型”**转移到了**“操作系统内核协议栈与硬件资源”。



## 1. C10K 问题（1999 年：调度与多路复用之战）

1999 年，计算机学者 Dan Kegel 正式提出 C10K 问题。当时主流服务器硬件通常只有 1~2 颗单核 CPU、不到 1GB 内存，面对互联网爆发式的访问增长，单机支撑 1 万连接成为难以逾越的鸿沟。



### 核心瓶颈

- **线程/进程模型崩溃**：当时主流架构是“一连接一线程/进程”（如早期 Apache 的 `prefork`）。操作系统单个线程栈默认占用约 1MB 到 8MB 内存，1 万个连接仅线程栈就需 10GB~80GB 内存，远超物理 RAM；同时，CPU 绝大部分时间被消耗在成千上万个线程的**上下文切换**上。
- **早期 I/O 多路复用低效（$O(N)$ 复杂度）**：原有的系统调用 `select` 和 `poll` 存在硬伤：
    1. `select` 默认有 1024 个文件描述符上限。
    2. 每次监听事件都需要把整个文件描述符集合在“用户态”与“内核态”之间全量拷贝。
    3. 内核与用户态都需要遍历整个集合去判断哪些连接有数据到达，时间复杂度为 $O(N)$。

### 核心解法

- **$O(1)$ 的就绪事件通知机制**：Linux 引入 `epoll`（2.6 内核）、FreeBSD 引入 `kqueue`、Windows 引入 `IOCP`。内核通过红黑树管理监听连接，并在网络数据到达触发硬件中断时，仅将活跃连接放入**就绪链表**中。应用只需读取就绪链表，时间复杂度降至 $O(1)$。
- **单线程事件驱动（Reactor 模式）**：以 Nginx、Node.js、Netty 为代表的非阻塞事件驱动框架诞生，仅用几个 Worker 线程即可轻松管理上万个并发连接。

## 2. C1000K 问题（2010 年代后：内核栈与硬件极限之战）

随着千兆/万兆网卡普及与多核大内存服务器普及，`epoll` 解决了一万连接的问题。但面对移动即时通讯（IM）、直播弹幕、物联网（IoT）的长连接网关场景，并发量级攀升至 100 万（C1M）甚至千万（C10M），瓶颈转移到了**操作系统内核层面**。



### 核心瓶颈

- **内核元数据与 Socket 缓冲区内存耗尽**：即使连接处于空闲状态，内核为每个 TCP 连接维护的 `struct sock`、`socket 读写缓冲区`（rmem/wmem）以及连接跟踪表（`nf_conntrack`）通常单连接就要占用 3KB~10KB。100 万空闲连接仅内核协议栈基础结构就要吞噬 3GB~10GB 内存。
- **软中断（SoftIRQ）风暴与 CPU 争用**：海量数据包到达网卡后，网卡产生硬件中断，内核转交给软中断（ksoftirqd）逐层走 TCP/IP 协议栈校验、分包、装配。CPU 核心会被软中断打满，无法把算力留给应用逻辑。
- **多核竞争与锁争用**：海量并发导致多个 CPU 核心频繁竞争全局哈希表锁、网卡中断队列与共享 `epoll` 实例。

### 核心解法

- **内核参数深度裁剪与调优**：
    - 放开系统级与进程级描述符上限（`fs.file-max`、`ulimit -n`）。
    - 压缩 TCP 读写缓冲区下限（`tcp_rmem` / `tcp_wmem`），关闭无用的内核模块（如防火墙连接跟踪 `nf_conntrack`）。
- **多队列与内核分流**：
    - 利用网卡多队列（RSS）将不同连接的中断硬分发至不同 CPU 核心。
    - 采用 `SO_REUSEPORT`，允许多个独立进程同时监听同一端口并由内核进行负载分发，消除多线程争抢单一 `epoll` 的惊群与锁竞争。
- **内核旁路（Kernel Bypass）**：
    - **DPDK（Data Plane Development Kit）**：彻底绕过 Linux 内核协议栈。网卡收包后，直接通过用户态驱动映射到用户空间，通过轮询模式（PMD）杜绝中断与系统调用的上下文切换。
    - **XDP / eBPF**：在网卡驱动层尚未进入内核协议栈之前，通过运行轻量级沙盒代码快速过滤或转发数据包。

## 关键技术对比

| **维度**             | **C10K 问题**                                                | **C1000K (C1M) 问题**                                        |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **主要挑战**         | 线程栈内存过大、CPU 上下文切换开销、`select`/`poll` $O(N)$ 轮询 | 内核 TCP 缓冲区膨胀、协议栈软中断过载、系统调用及跨核锁竞争  |
| **突破瓶颈的核心层** | **用户态调度模型**（线程模型 $\to$ 异步事件驱动）            | **内核态网络栈**（内核调优 $\to$ 内核分流 $\to$ 内核旁路）   |
| **底层核心技术**     | `epoll`、`kqueue`、Reactor 模式                              | `SO_REUSEPORT`、网卡多队列（RSS）、DPDK、XDP/eBPF、`io_uring` |
| **代表性框架/系统**  | Nginx, Redis, Netty, Node.js                                 | DPDK, F-Stack, Envoy, Seastar                                |
