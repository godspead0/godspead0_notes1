你想了解的**代码设计原则**，核心是面向对象开发的通用指导准则（也适配非 OOP 语言的设计思路），目的是让代码更**易维护、易扩展、高复用、低耦合**，避免后期需求变更时出现 “牵一发而动全身” 的烂代码。

这些原则中，**SOLID 五大原则**是基础核心，再加上工业界最常用的**迪米特法则**和**合成复用原则**，这 7 个是日常开发、面试高频的核心原则。我会用**通俗大白话 + Java 代码反例 + 正例**讲解，每个原则包含**核心定义、通俗理解、代码示例、使用注意**，贴合实际开发场景，新手也能快速理解，同时会标注原则的**核心关键词**和**避坑点**（比如避免过度设计）。

### 一、SOLID 五大核心原则（面向对象基础）

SOLID 是 5 个原则的英文首字母缩写，是最基础、最核心的设计原则，所有其他原则都是其延伸。

#### 1. 单一职责原则（Single Responsibility Principle，SRP）

- **核心定义**：一个类 / 方法 / 模块，只负责**一个单一的功能职责**，只有**一个引起它变化的原因**。

- **通俗理解**：一个类就干一件事，比如 “用户管理类” 只处理用户的 CRUD，不要同时处理发邮件、记录日志。

- 反例

    ：一个类同时负责用户管理和邮件发送，两个职责耦合，改邮件逻辑可能影响用户管理。

    java

    

    运行

    

    

    

    

    ```
    // 反例：一个类承担2个职责（用户管理+邮件发送）
    public class UserService {
        // 职责1：用户新增
        public void addUser(String username) {
            System.out.println("新增用户：" + username);
        }
        // 职责2：发送注册邮件（和用户管理无关）
        public void sendRegisterEmail(String email) {
            System.out.println("给" + email + "发送注册邮件");
        }
    }
    ```

    

- 正例

    ：拆分出独立的

    ```
    EmailService
    ```

    ，每个类只负责自己的职责，变化互不影响。

    java

    

    运行

    

    

    

    

    ```
    // 正例：单一职责 - 只处理用户管理
    public class UserService {
        public void addUser(String username) {
            System.out.println("新增用户：" + username);
        }
    }
    // 正例：单一职责 - 只处理邮件发送
    public class EmailService {
        public void sendRegisterEmail(String email) {
            System.out.println("给" + email + "发送注册邮件");
        }
    }
    ```

    

- **使用注意**：不要过度拆分（比如一个简单的工具方法拆成一个类），以 **“是否会因为不同原因修改”** 为拆分标准。

#### 2. 开闭原则（Open Closed Principle，OCP）

- **核心定义**：软件实体（类、模块、方法）对**扩展开放**，对**修改关闭**。

- **通俗理解**：新增功能时，通过**新增代码**实现，而不是**修改原有稳定的代码**（原有代码已经过测试，修改易引入 bug）。

- **核心实现**：依赖**抽象（接口 / 抽象类）**，而不是具体实现，通过新增实现类扩展功能。

- 反例

    ：计算器类新增 “乘法” 功能，需要修改原有代码，违反开闭。

    java

    

    运行

    

    

    

    

    ```
    // 反例：新增运算需要修改原有类
    public class Calculator {
        // 只有加减运算，新增乘法要改这个方法
        public int calculate(int a, int b, String op) {
            if ("add".equals(op)) return a + b;
            if ("sub".equals(op)) return a - b;
            throw new IllegalArgumentException("不支持的运算");
        }
    }
    ```

    

- 正例

    ：定义运算接口，新增乘法只需新增实现类，原有代码无需修改。

    java

    

    运行

    

    

    

    

    ```
    // 步骤1：定义抽象接口（扩展的入口）
    public interface Operation {
        int compute(int a, int b);
    }
    // 步骤2：原有实现类（无需修改）
    public class AddOperation implements Operation {
        @Override
        public int compute(int a, int b) { return a + b; }
    }
    public class SubOperation implements Operation {
        @Override
        public int compute(int a, int b) { return a - b; }
    }
    // 步骤3：新增乘法（只加代码，不修改原有）
    public class MulOperation implements Operation {
        @Override
        public int compute(int a, int b) { return a * b; }
    }
    // 计算器类（依赖抽象，无需修改）
    public class Calculator {
        public int calculate(int a, int b, Operation op) {
            return op.compute(a, b);
        }
    }
    ```

    

- **使用注意**：开闭原则是**所有设计原则的核心**，设计模式（如工厂、策略）都是为了实现开闭。

#### 3. 里氏替换原则（Liskov Substitution Principle，LSP）

- **核心定义**：子类可以**完全替换**父类，且替换后**程序的逻辑行为不变、正确性不受影响**。

- **通俗理解**：父类能做的事，子类必须能做，且子类不能改变父类的**核心行为约定**（比如父类定义 “加法是求和”，子类不能重写成 “求差”）。

- **核心本质**：约束**继承的合理性**，避免滥用继承（继承的前提是 “is-a” 关系，而不是简单的代码复用）。

- 反例

    ：子类重写父类方法，改变了原有逻辑，替换后程序出错。

    java

    

    运行

    

    

    

    

    ```
    // 父类：鸟，定义“会飞”的行为
    public class Bird {
        public void fly() {
            System.out.println("鸟会飞");
        }
    }
    // 反例：企鹅是鸟，但不会飞，重写fly抛出异常，违反里氏替换
    public class Penguin extends Bird {
        @Override
        public void fly() {
            throw new UnsupportedOperationException("企鹅不会飞");
        }
    }
    // 调用方：传入Bird，预期会飞，传入Penguin则报错
    public class Test {
        public static void letBirdFly(Bird bird) {
            bird.fly(); // 传入Penguin，程序崩溃
        }
    }
    ```

    

- 正例

    ：重新设计继承体系，拆分抽象，让子类符合 “is-a”。

    java

    

    运行

    

    

    

    

    ```
    // 步骤1：顶层抽象：动物（无飞的行为）
    public abstract class Animal {
        public void eat() { System.out.println("动物会吃"); }
    }
    // 步骤2：拆分出“会飞的鸟”，继承动物
    public class FlyableBird extends Animal {
        public void fly() { System.out.println("会飞的鸟飞"); }
    }
    // 步骤3：企鹅是动物，不是“会飞的鸟”，无需实现fly
    public class Penguin extends Animal {
        // 只继承eat，无fly方法，符合实际
    }
    // 调用方：只给会飞的鸟传参，不会出错
    public class Test {
        public static void letFlyableBirdFly(FlyableBird bird) {
            bird.fly();
        }
    }
    ```

    

- **使用注意**：继承的核心是**行为的复用和约定**，不是代码的简单复制；如果子类需要重写父类方法并改变核心逻辑，说明继承关系设计错误。

#### 4. 接口隔离原则（Interface Segregation Principle，ISP）

- **核心定义**：客户端不应该依赖它**不需要的接口**；一个大而全的接口，要拆分成**多个小的、专用的接口**。

- **通俗理解**：不要设计 “万能接口”，比如 “动物接口” 不要包含 “飞、游、跑” 所有方法，让鸟实现飞，鱼实现游，避免实现类被迫重写无关方法。

- 反例

    ：大接口包含所有方法，实现类被迫实现自己不需要的方法（空实现 / 抛异常）。

    java

    

    运行

    

    

    

    

    ```
    // 反例：万能动物接口，包含所有行为
    public interface Animal {
        void fly(); // 飞
        void swim(); // 游
        void run(); // 跑
    }
    // 鸟只会飞，被迫实现swim和run（空实现，冗余）
    public class Bird implements Animal {
        @Override public void fly() { System.out.println("飞"); }
        @Override public void swim() {} // 冗余
        @Override public void run() {} // 冗余
    }
    ```

    

- 正例

    ：拆分成多个专用小接口，实现类按需实现，无冗余。

    java

    

    运行

    

    

    

    

    ```
    // 正例：拆分成专用小接口
    public interface Flyable { void fly(); }
    public interface Swimmable { void swim(); }
    public interface Runnable { void run(); }
    // 鸟只实现Flyable，无冗余
    public class Bird implements Flyable {
        @Override public void fly() { System.out.println("飞"); }
    }
    // 鱼只实现Swimmable
    public class Fish implements Swimmable {
        @Override public void swim() { System.out.println("游"); }
    }
    // 狗实现Runnable和Swimmable
    public class Dog implements Runnable, Swimmable {
        @Override public void run() { System.out.println("跑"); }
        @Override public void swim() { System.out.println("狗刨"); }
    }
    ```

    

- **使用注意**：接口拆分的粒度以 **“客户端的实际需求”** 为标准，不要过度拆分（比如一个方法拆成一个接口）。

#### 5. 依赖倒置原则（Dependency Inversion Principle，DIP）

- **核心定义**：① 高层模块不依赖低层模块，二者都依赖**抽象**；② 抽象不依赖细节，细节依赖**抽象**。

- **通俗理解**：不要直接依赖具体的类，要依赖**接口 / 抽象类**，比如 “电脑不依赖具体的鼠标品牌（罗技、雷柏），只依赖鼠标的 USB 接口”。

- **核心作用**：解决**高层模块和低层模块的紧耦合**问题，低层模块的替换不会影响高层模块。

- 反例

    ：高层模块

    ```
    Computer
    ```

    直接依赖低层模块

    ```
    LogitechMouse
    ```

    （罗技鼠标），换雷柏鼠标需要修改

    ```
    Computer
    ```

    代码。

    java

    

    运行

    

    

    

    

    ```
    // 反例：低层模块：具体的罗技鼠标
    public class LogitechMouse {
        public void click() { System.out.println("罗技鼠标点击"); }
    }
    // 高层模块：电脑，直接依赖罗技鼠标（紧耦合）
    public class Computer {
        private LogitechMouse mouse;
        public Computer(LogitechMouse mouse) { this.mouse = mouse; }
        public void useMouse() { mouse.click(); }
    }
    ```

    

- 正例

    ：定义鼠标抽象接口，高层

    ```
    Computer
    ```

    依赖抽象，低层模块（罗技、雷柏）实现抽象，替换鼠标无需修改高层。

    java

    

    运行

    

    

    

    

    ```
    // 步骤1：定义抽象接口（鼠标标准）
    public interface Mouse {
        void click();
    }
    // 步骤2：低层模块：实现抽象（罗技、雷柏鼠标）
    public class LogitechMouse implements Mouse {
        @Override public void click() { System.out.println("罗技鼠标点击"); }
    }
    public class RapooMouse implements Mouse {
        @Override public void click() { System.out.println("雷柏鼠标点击"); }
    }
    // 步骤3：高层模块：依赖抽象，不依赖具体
    public class Computer {
        private Mouse mouse;
        // 构造注入抽象，支持任意实现类
        public Computer(Mouse mouse) { this.mouse = mouse; }
        public void useMouse() { mouse.click(); }
    }
    // 使用：替换鼠标只需传不同实现类，Computer代码不变
    public class Test {
        public static void main(String[] args) {
            Computer c1 = new Computer(new LogitechMouse());
            c1.useMouse(); // 罗技鼠标点击
            Computer c2 = new Computer(new RapooMouse());
            c2.useMouse(); // 雷柏鼠标点击
        }
    }
    ```

    

- **使用注意**：依赖倒置是 ** 控制反转（IOC）、依赖注入（DI）** 的设计基础，Spring 框架的核心就是依赖倒置。

### 二、另外 2 个高频通用原则

除了 SOLID，**迪米特法则**和**合成复用原则**是日常开发中解决 “耦合” 和 “继承滥用” 的关键原则，和 SOLID 互补。

#### 6. 迪米特法则（Law of Demeter，LOD）/ 最少知道原则

- **核心定义**：一个对象应该**最少知道**其他对象的信息，只和**直接朋友**交互（直接朋友：成员变量、方法参数、返回值，不是局部变量）。

- **通俗理解**：不要 “跨级调用”，比如 “订单类” 要操作库存，直接调用 “库存服务类” 的方法即可，不要通过库存服务去调用库存的底层 DAO 方法。

- **核心作用**：降低对象之间的**直接耦合**，减少代码的维护成本（一个对象的修改，只会影响其直接朋友）。

- 反例

    ：跨级调用，订单类直接操作库存 DAO（非直接朋友），耦合度高。

    java

    

    运行

    

    

    

    

    ```
    // 库存DAO（底层类）
    public class StockDao {
        public void reduceStock(int skuId, int num) {
            System.out.println("扣减库存：" + skuId + "，数量：" + num);
        }
    }
    // 库存服务（直接朋友）
    public class StockService {
        public StockDao stockDao = new StockDao(); // 库存服务的直接朋友
    }
    // 反例：订单服务跨级调用库存DAO（非直接朋友）
    public class OrderService {
        public void createOrder(int skuId, int num) {
            StockService stockService = new StockService();
            // 跨级调用：订单服务直接操作库存DAO（非直接朋友），违反迪米特
            stockService.stockDao.reduceStock(skuId, num);
        }
    }
    ```

    

- 正例

    ：订单类只和直接朋友（库存服务）交互，库存服务封装底层 DAO 调用。

    java

    

    运行

    

    

    

    

    ```
    // 库存DAO（底层类，私有化）
    public class StockDao {
        public void reduceStock(int skuId, int num) {
            System.out.println("扣减库存：" + skuId + "，数量：" + num);
        }
    }
    // 库存服务：封装底层DAO，对外提供统一方法（直接朋友）
    public class StockService {
        private StockDao stockDao = new StockDao(); // 私有化，不对外暴露
        // 对外提供扣减库存的方法
        public void deductStock(int skuId, int num) {
            stockDao.reduceStock(skuId, num);
        }
    }
    // 正例：订单服务只和直接朋友（StockService）交互
    public class OrderService {
        public void createOrder(int skuId, int num) {
            StockService stockService = new StockService();
            stockService.deductStock(skuId, num); // 只调用直接朋友的方法
        }
    }
    ```

    

- **使用注意**：迪米特法则的核心是**封装**，通过封装隐藏对象的内部细节，只暴露对外的公共方法。

#### 7. 合成复用原则（Composite Reuse Principle，CRP）/ 组合 / 聚合复用原则

- **核心定义**：优先使用**组合（has-a）\**或\**聚合（contains-a）\**实现代码复用，而不是\**继承（is-a）**。

- **通俗理解**：“汽车需要发动机”，不要让汽车**继承**发动机，而是让汽车**组合**一个发动机对象（汽车有一个发动机），通过调用发动机的方法实现复用。

- **核心作用**：解决继承的**弊端**（继承会导致父类的变化传递给子类，耦合度高；Java 是单继承，限制扩展）。

- 反例

    ：滥用继承实现代码复用，汽车继承发动机，耦合度高，且不符合 “is-a”（汽车不是发动机）。

    java

    

    运行

    

    

    

    

    ```
    // 发动机类
    public class Engine {
        public void start() { System.out.println("发动机启动"); }
    }
    // 反例：汽车继承发动机（违反is-a，耦合度高）
    public class Car extends Engine {
        public void run() {
            start(); // 复用发动机的start方法
            System.out.println("汽车行驶");
        }
    }
    ```

    

- 正例

    ：汽车

    组合

    发动机对象，通过调用对象方法实现复用，低耦合，易扩展（可替换不同发动机）。

    java

    

    运行

    

    

    

    

    ```
    // 发动机接口（抽象，方便扩展）
    public interface Engine {
        void start();
    }
    // 汽油发动机实现
    public class GasolineEngine implements Engine {
        @Override public void start() { System.out.println("汽油发动机启动"); }
    }
    // 电动发动机实现
    public class ElectricEngine implements Engine {
        @Override public void start() { System.out.println("电动发动机启动"); }
    }
    // 正例：汽车组合发动机对象（has-a），优先组合复用
    public class Car {
        private Engine engine; // 组合发动机对象
        // 构造注入，支持替换不同发动机，易扩展
        public Car(Engine engine) { this.engine = engine; }
        public void run() {
            engine.start(); // 复用发动机的方法
            System.out.println("汽车行驶");
        }
    }
    // 使用：替换发动机只需传不同实现类
    public class Test {
        public static void main(String[] args) {
            Car gasCar = new Car(new GasolineEngine());
            gasCar.run(); // 汽油发动机启动 → 汽车行驶
            Car elecCar = new Car(new ElectricEngine());
            elecCar.run(); // 电动发动机启动 → 汽车行驶
        }
    }
    ```

    

- **使用注意**：继承不是不能用，而是**优先组合**；当存在明确的 “is-a” 关系（比如猫是动物），可以用继承；当只是需要复用代码（比如汽车需要发动机），用组合。

### 三、设计原则的核心注意点（新手必看，避坑关键）

1. **原则是指导，不是硬性规定**：所有原则的最终目的是**提升代码质量**，不是为了遵守而遵守，比如简单的工具类（如`StringUtil`），无需拆分多个类，避免**过度设计**。
2. **原则之间相互关联，并非孤立**：比如实现**开闭原则**需要依赖**依赖倒置原则**和**里氏替换原则**，**接口隔离原则**是**单一职责原则**在接口上的体现。
3. **平衡原则和开发效率**：小型项目 / 快速迭代的业务，无需严格遵守所有原则（比如快速实现功能为主）；中大型项目 / 长期维护的业务，必须遵守核心原则（否则后期维护成本极高）。
4. **设计模式是原则的落地实现**：所有设计模式（如工厂、策略、单例）都是为了更好地遵守这些设计原则，比如策略模式实现**开闭原则**，工厂模式实现**依赖倒置原则**。

### 总结

代码设计原则的核心目标是**低耦合、高内聚、可维护、可扩展**，7 个核心原则的**极简记忆版**如下，日常开发中能落地这几点，代码质量会大幅提升：

1. **单一职责**：一个类 / 方法只干一件事；
2. **开闭原则**：新增功能加代码，不修改原有代码；
3. **里氏替换**：子类能完全替换父类，不改变原有逻辑；
4. **接口隔离**：接口拆小，按需实现，无冗余；
5. **依赖倒置**：依赖抽象（接口 / 抽象类），不依赖具体实现；
6. **迪米特法则**：少知道、少交互，只和直接朋友打交道；
7. **合成复用**：优先组合 / 聚合，少用继承，降低耦合。
